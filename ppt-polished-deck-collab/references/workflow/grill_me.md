# Grill-Me 交互式 Deck Intake

本文定义新建 deck 与重大重构的提问阶段。`/grill-me`、`grill me` 和 `深度定制` 是显式别名，但新 deck 即使没有使用别名，也默认遵循本协议；明确的小范围修改除外。

## 目录

- 阶段门
- 决策模型
- 单题协议
- 自适应顺序
- 预览协议
- 大纲交接
- 停止与恢复

## 阶段门

只使用一个顶层流程：

`提问 -> 生成大纲 -> 反馈 -> 执行大纲产出结果 -> 评价与修正`

用户只提供主题时，不得同轮生成完整 PPT。完整 brief 可以缩短提问，但不能跳过可执行大纲、反馈和明确批准。“直接做”“自由发挥”等前置授权允许 agent 推荐默认项，不批准用户尚未看到的大纲。

纯文字纠错、格式修复和边界明确的单页修改，只询问完成该修改必需的信息，不启动完整访谈。

扫描请求与已有材料后，先初始化 workspace，再记录答案、生成预览或审计模板。流程状态写入 `deck_narrative.md` frontmatter；面向人的访谈摘要写入 `brief.md`。

## 决策模型

提问前检查用户提示、附件、现有 PPT、模板、品牌资料、数据源和 workspace。内部将待处理事项分为：

- `known`：用户或材料已经证明。
- `derived`：可由证据或上游答案推导，并能披露推导依据。
- `decision_needed`：不同答案会实质改变结果。
- `defaultable`：用户无偏好时可安全采用低风险推荐。
- `unresolved`：当前无法查明，也不能安全默认。

不要询问 `known`。`derived` 不逐项反问用户，在共同理解摘要中披露结果和依据；每次收到新答案后重新计算依赖关系。

问题必须至少改变以下一项：研究范围、证据标准、叙事、文案体验、信息密度、视觉方向、资产路线、可编辑性、交付或验证。不会改变结果的低影响偏好不进入访谈。

## 单题协议

每轮只提出一个问题并等待回答。宿主有交互式提问工具时优先使用；不可用时以普通文本询问同一个问题。

每题遵循：

1. 提供 2-3 个互斥且有效的选项，并允许自定义回答。
2. 推荐项放在首位，用一句当前上下文说明推荐依据。
3. 选项描述用户可选择的结果，不暴露内部字段或 agent 动作清单。
4. 接受“采用推荐项”“跳过本题”“其余采用推荐默认”“结束访谈”及其它语言中的同义指令。
5. 记录答案、受影响决策和下游变化，不重复询问同一事实。

“跳过本题”只对 `defaultable` 采用推荐值；不能安全省略的事项保持 `unresolved`。“结束访谈”停止提问，汇总已知、默认和未决项，把状态设为 `stopped`，且不开始 build。

## 自适应顺序

按依赖关系由浅入深推进，而不是照抄固定问卷：

1. 范围：页数或时长、语言、比例、截止方式和主要用途。
2. 受众与结果：目标读者、希望促成的行动或理解、成功信号和不能失败的结果。
3. 证据边界：时间、地域、对象定义、比较基准、来源等级、估算、引用和免责声明。
4. 叙事：主判断、目标决策、必须强调与避免、因果和不确定性边界。
5. 阅读体验：现场讲解或独立阅读、快速抓重点或完整推导、正文与附录分工、语气和证据页深度。
6. 视觉方向：模板或品牌边界、层级、图片 / 图表 / diagram 比例、信息密度和可编辑性。
7. 交付与验证：可编辑对象、文件格式、预览和必需检查。

在最早仍活跃的阶段中，只询问影响最大的未决项。后续发现会改变结论的歧义时，可以回到较早阶段。

## 预览协议

只有预览能帮助用户做出高影响决定时才生成；不得把预览扩展为未经批准的局部成品。

视觉方向未锁定且风险较高时：

- 提供 2-3 个实质不同的候选方向。存在用户模板或真实参考时，每个方向绑定对应来源；没有参考时，定义可用原生对象实现且保持可编辑的不同视觉系统。
- 所有候选固定同一事实、页面任务、核心文案和证据边界。
- 先比较一张代表页；暂定一个方向后，仅在确有必要时用 hero / evidence / complex 验证其适用范围。
- 所有产物标记 `NON-FINAL STYLE PREVIEW`，示意数据必须明确标注。
- 展示后只问一个比较问题，并记录选中方向、淘汰项和理由。

品牌或正式模板已经锁定视觉系统时，只总结继承约束和允许变化的范围，不为凑数量制造虚假备选。模板选择或预览满意都不等于大纲批准。

## 大纲交接

所有高影响事项均为 `known`、`derived` 或已明确采用默认后，先输出共同理解摘要：

- 已确认事实和用户选择；
- Agent 推导与依据；
- 接受的默认值；
- 未决项和 blocker；
- 预览决定与仍未验证的视觉风险。

随后生成一份可执行制作大纲，至少覆盖目标、受众、证据计划、章节叙事、逐页 `page_task` / `reader_question` / `key_message`、页面可见文案方向、资产、layout / 密度、可编辑构建路线、验证、假设和交付物。

生成后把 `workflow.state` 设为 `outline_ready`，赋值或递增 `workflow.outline_version`；展示完整大纲后进入 `awaiting_outline_feedback`。根据反馈修订受影响部分。只有用户明确批准当前完整版本时，批准才有效：

```yaml
workflow:
  state: outline_approved
  outline_version: "v1"
  approval:
    status: approved
    outline_version: "v1"
    evidence: "<用户批准原话或持久化会话引用>"
    approved_at: "<可用时填写 ISO-8601 时间>"
```

大纲发生实质修改时，递增 `outline_version`，将批准重置为 `pending`，并返回反馈阶段。资产生产或 PPT 组装前运行 `validate_workflow_gate.py --target build --require-workflow`。

成品进入 `reviewing` 或 `final` 后不得直接重新 build。需要修正时先转入 `revising`；如果修正改变大纲中的高影响决策，再递增大纲版本并重新取得批准。

## 停止与恢复

只使用以下状态：`questioning`、`outline_ready`、`awaiting_outline_feedback`、`outline_approved`、`executing`、`reviewing`、`revising`、`final`、`blocked`、`stopped`。

恢复任务时先读取持久化 workflow 与 intake summary，从最早的高影响未决项继续，不重放问卷。`stopped` 需要用户明确要求恢复；`blocked` 需要先消除 blocker 或由用户明确接受相关风险。
